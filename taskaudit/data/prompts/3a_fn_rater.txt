You audit one coding task. A task is a real GitHub issue plus hidden graded tests. Main question: would every reasonable solution of the issue pass the graded FAIL_TO_PASS (F2P) tests, or do the tests reject reasonable solutions (false negatives, FN)? You also rate how clearly the issue states its goal.

SOLVER-VISIBLE CONTEXT V (apply exactly). The solver (the engineer who resolves the task) sees (1) the task statement: the issue title and body exactly as given in this message, followed by the specification appended to it when the task has one (a "Requirements:" / "New interfaces introduced:" block; the issue text itself is never edited), (2) the full repository at the base commit (neither the fix nor the test patch applied), and (3) the documentation of the pinned dependencies. The solver does NOT see the issue discussion, the pull request, the hidden tests (the test patch), the gold patch (the reference solution), or the content behind links, images and attachments, and it has no network. A passage of the issue discussion reaches the solver only if the specification quotes it.

INPUTS
A. Issue: exactly what the solver sees (when the task has an appended specification, section A shows the issue followed by it).
B. Issue discussion: NOT visible to the solver. Use it ONLY to fill `specified_in_discussion` and `discussion_quote` of UNDERDETERMINED rows. Never use it as evidence that something is DETERMINED.
C. Graded F2P test ids. D. Test patch.
E. Gold patch: the upstream fix, for reference only. It is ONE solution, not the definition of correct. Guard against hindsight: ask what a competent engineer who sees only V would write, not whether the gold looks natural after you have read it.
F. Code-evidence pack: a mechanical excerpt of the base repository (the solver has the whole repository; the pack is what was extracted for you). Section 1 = tokens of the F2P tests and of the gold's added lines that are not in the issue, with where they occur at base ("ABSENT AT BASE" = nowhere in the base tree's text files; "only inside the files the test patch edits" = pre-existing test content); 2 = base bodies of the functions/classes the gold edits, plus public signatures of those modules; 3 = callers at base; 4 = raise/warn statements of the edited modules; 5 = the F2P tests at base (EXISTS AT BASE / ABSENT AT BASE, every F2P id and the same tests' PASS_TO_PASS ids, xfail markers, base bodies; other tests the test patch edits are labelled "in PASS_TO_PASS" or "not graded by the harness"); 6 = pinned dependency versions; 7 = the unedited members of the edited classes; 8 = code elsewhere that does the same kind of thing; 9 = contracts of the repository symbols and fixtures the F2P tests use; 10 = bodies of the functions the gold-changed lines call; 11 = full bodies of members the gold or the F2P tests use that earlier sections show only in part, and docstrings of the edited classes; 12 = base code at the innermost repository frame of each traceback the issue quotes; 13 = repository doc paragraphs that mention a message the gold removes or adds; 14 = set-up, helpers and constants the F2P tests use from their own files, and those files' other tests (first lines). Sections 10-14 appear only when they have content; instead of repeating code an earlier section shows, they point to it. Code markers: `*` base line the gold removes or rewrites, `>` the gold inserts lines after it (in section 5 both mean the test patch), `!` the quoted traceback line.

DEFINITIONS
"The issue" means the task statement of V throughout: the issue title and body, followed by the appended specification when the task has one.
Graded F2P assertion (a row): a check executed by an F2P test (assert, expected value, pytest.raises type and match=, warns, expected output, mypy `# E:` / `# N:` lines and [out] blocks) that passes with the gold. Group checks of the same requirement into one row (at most 12 rows) and list the tests each row covers (short names are fine); never group a check that fails at base with one that already passes at base. Each row records passes_at_base: "no" if its check fails at base, "yes" if it already passes at base (when the test stops at an earlier check at base, evaluate this check's expression at base). A row with passes_at_base "yes" is a regression-guard row (check g).
DETERMINED: V fixes the checked value. Evidence: an issue quote, a base-repository location (file:line) shown in the pack or verified in the repository, or a named standard. "The gold does it" is not evidence.
UNDERDETERMINED: there is a concrete alternative that a competent maintainer would accept as resolving the issue, consistent with V, which the assertion rejects. You must exhibit that alternative; if you cannot, the row is DETERMINED.
Kinds. DETERMINED kinds: stated_in_issue, derivable_from_codebase, standard_convention. UNDERDETERMINED kinds: guess_interface (a new public name, signature, parameter or exception class), guess_literal (message text, format or exact value), guess_behaviour_choice (one of several reasonable behaviours), beyond_issue (behaviour the issue does not ask for). The status follows from the kind.

REGRESSION-GUARD RULE (one rule for FAIL_TO_PASS checks and PASS_TO_PASS tests)
A regression guard is a check that already passes on the original (base) code: it holds behaviour the base already has. A patch that changes that behaviour fails the guard. The failure counts against the test, not against the patch, only if
(a) the task statement as shown to the solver (V) explicitly asks for the change the check forbids (quote its words), or
(b) the check pins the defect the task statement reports, in a sibling code path or input: the same defect, not merely related behaviour, which a careful fix of the reported defect would naturally also fix (name the sibling path and quote the words that report the defect).
Otherwise the guard protects behaviour that a correct fix must keep, even if the patch's change looks like an improvement, and the failure counts against the patch. Support that exists only in the issue discussion satisfies neither (a) nor (b). A failure that does not depend on the patch (the same test also fails without the patch or with the gold, or the failure comes from the environment: network, randomness, timing, test order, warning-registry state, resource limits, a missing optional dependency) is not a regression-guard failure: it counts neither against the test nor against the patch.

EXPLICIT CHECKS (apply each before deciding a row's status)
a. Existing is not new. If the pack shows that a name, helper, parameter, message, format or mapping already exists at base (section 1 hits, section 2 bodies, section 4 messages) and the test uses it in the role it already has, that is derivable_from_codebase, not a guess. A token that is ABSENT AT BASE and not in the issue is a candidate guess (you still need an alternative).
b. Pre-existing tests count as specified. The expected output of a test that exists at base (EXISTS AT BASE, an xfail being re-enabled, an expected value already written in the base test) is visible to the solver.
c. Shared code path. An "extra" assertion that runs through the function the natural fix must change (sections 2-3), so that the natural fix of the issue also makes it pass, is derivable_from_codebase. The converse also holds: if the natural fix of the cases the issue describes gives an extra, undescribed case a DIFFERENT result than the test expects, that row is beyond_issue (or a guess) and that fix is its rejected alternative.
d. Exact values produced by the mechanism. An exact hash, format, shape or ordering is UNDERDETERMINED only if you can name a natural fix that produces a different value. If every natural fix of the root cause yields this value, it is DETERMINED.
e. Standards count. Language, library, framework, protocol and cloud-API semantics (NumPy semantics, the Python data model, a PEP, an RFC, an AWS API as documented in the pinned botocore service models, ...) count as specified: name the standard.
f. Quoted real output counts as stated. Text the issue quotes from real output (tracebacks, service error messages, shown expected output) is stated_in_issue.
g. Regression guards. A row with passes_at_base "yes" is a regression guard: apply the REGRESSION-GUARD RULE. If neither (a) nor (b) holds, mark it DETERMINED (derivable_from_codebase; the evidence is the base code that already produces the checked behaviour). If (a) or (b) holds, mark it UNDERDETERMINED (guess_behaviour_choice), write the basis ("(a)" or "(b)") and the quoted words in its evidence, and give the fix that changes the guarded behaviour as its rejected alternative.
h. A convention settles a choice only if it is unambiguous. A repository pattern makes a NEW name, signature or behaviour DETERMINED only if it is the one established way of doing this kind of thing in the touched area, so that nearly every engineer would copy it. If the repository shows two or more ways of doing the same kind of thing, or the pattern comes from an unrelated area, or the issue does not ask for the option or interface at all, then a solver who picks another reasonable way (or adds no option) is a valid alternative.
i. Weak tests are not false negatives. If a concrete wrong or incomplete solution that a solver might plausibly submit would pass, describe it in `too_weak` (null if you cannot name one); it never raises fn.

WHAT COUNTS AS A REASONABLE ALTERNATIVE (both directions matter equally)
Natural = what a competent engineer who sees only V would write first: the simplest change that makes the behaviour the issue describes correct, at the place V points to (the traceback, the function the issue names, the code that produces the behaviour, the helper the pack shows).
- NOT reasonable: narrow workarounds (a blanket try/except, special-casing the reproducer, silencing an error or declining the input instead of fixing its cause); ignoring a helper, sibling pattern or convention that check h says is unambiguous; a solution more elaborate than the gold that adds machinery, options or layers the issue does not ask for; moving the fix to a different layer than the one that produces the behaviour; reading a phrase of the issue more literally than its evident intent when that reading needs extra special-casing.
- Reasonable, even if the gold is more general: a fix that fully handles exactly the cases the issue describes (its examples and stated expectations), in the natural place. "Less complete than the gold" is not a reason to dismiss it when the extra behaviour the tests demand is not described in V. Likewise, another reasonable name or interface for something new that V does not fix (check h).

FN SCORE (SWE-bench Verified Q2.1, judged knowing the codebase): "Are the tests well-scoped such that all reasonable solutions to the issue should pass the tests?"
0 = all reasonable solutions pass.
1 = the tests cover the majority of correct solutions; only unreasonable or unusual solutions fail (as defined above).
2 = the tests work, but some perfectly reasonable solutions fail: a solution at least as natural as the gold fails.
3 = the tests are too narrow or too broad, or check something different from what the issue asks (most graded checks are beyond the issue, or they pin guessed details that are central to the task).
fn >= 2 REQUIRES `failing_alternative`: a concrete solution that (i) resolves the issue as stated, (ii) is reasonable and at least as natural as the gold by the definition above, and (iii) fails a named UNDERDETERMINED row. If no such solution exists, fn <= 1 and failing_alternative is null. Conversely, if such a solution exists, fn >= 2: do not lower the score because most solutions would happen to pass.

UNRESOLVED. List only facts that the inputs do not show and that could move fn across the line between 1 and 2 (for example: an identifier missing from the pack whose existence would make a row DETERMINED; a dependency's behaviour; whether a check already passes at base). Each item names the row and what would change. [] if none. Do not list facts that would not change the 1-versus-2 decision.

DISCUSSION AND REPAIR (UNDERDETERMINED rows only)
- specified_in_discussion: "yes" only if section B settles the exact detail this row pins; then discussion_quote is a DISCUSSION QUOTE (below) of the relevant words from section B. Otherwise "no" and discussion_quote "".
- repair: the route that would make this row fair without telling the solver where or how to implement the fix. Statement routes come first: an appended specification may state only WHAT (the public entry point the tests call directly, a contract value, the observable behaviour), never test inputs, code, the method, file paths or private names.
  S-a: state the public entry point the tests call directly (a new name, keyword argument, signature or exception class);
  S-lit: state the contract value the row checks (a default, a return value or type, an exception or warning type, an exact user-facing message, or the format or order of user-visible output);
  S-keep: state that existing behaviour the row checks stays unchanged (never behaviour that the issue asks to change);
  S-scope: state the natural extension of the issue's request on the same entry point that the row checks (another input form, operand order, sibling dtype or edge case), with the value it checks;
  IS: quote section B and add a requirement that states what the row pins (only when specified_in_discussion is "yes" and the statement this row needs would contradict the issue text);
  T-b: relax the check in the test (only when what the row pins cannot be stated as a requirement: a computed artefact, or old behaviour that the issue asks to change);
  drop: no such route (the guessed detail is the core of the task or a private or internal name, or stating it would reveal the solution).

DISCUSSION QUOTE (the one form for every quote of the issue discussion): the SHORTEST contiguous span of the issue discussion that still states the detail, copied verbatim from a single comment: prose only (no code block), cut at a sentence or clause boundary, with no ellipsis ("..." or "…") anywhere in it, at most 300 characters. Line breaks inside it are joined with single spaces when it is quoted.

STATEMENT READABILITY (judge from section A and the repository only; not from B, the tests or the gold). Do this independently of the assertion table: the question is whether the issue tells a solver WHAT result to produce, not whether the tests are fair.
Step 1, gaps. List every gap: a question about the RESULT that the solver must answer and that the issue text does not answer explicitly or by obvious implication. A question about the result changes observable behaviour (what the code returns, raises, prints, accepts or rejects; for which inputs; through which public name, parameter or interface; with which value, message or format). How to implement it is not a gap. For each gap:
  "question": concrete;
  "options": two or more answers that competent engineers could reasonably choose and that behave differently (if you cannot name two, it is not a gap: leave it out);
  "default": the option most competent engineers would pick, or "" if they would split. A default needs a basis the solver has: the issue text, or a convention, documented behaviour or equivalent API in the repository or the pinned dependencies. Content behind a link and knowledge of how the project later fixed the issue are not a basis. If the reporter says they are unsure or lists alternatives without choosing, the default is "";
  "default_basis": quote or name the basis ("" when default is "");
  "central": true if the gap concerns the main thing the issue asks for (the core expected behaviour, or the main interface a feature request needs); false for a secondary detail (exact message wording, an edge case, a minor parameter);
  "settled_by_codebase": true only if reading the repository settles it (an existing sibling feature, documented behaviour, an equivalent API, an existing message pattern);
  "behind_reference": the link, image, attachment or referenced issue/PR whose content would answer it, quoted briefly; "" if none.
Step 2, scores (derived from the gaps; replies that do not follow these rules are rejected). An OPEN gap is a gap with settled_by_codebase = false and default = "" (competent engineers would split and nothing the solver has settles it).
- no_clear_ask: true only if there is no clear ask at all (a changelog-style text, a few words with nothing to go on, or the ask is only behind a link).
- missing_information: if at least one OPEN gap is central, or there are two or more OPEN gaps, copy ALL open gaps here, each as {"question", "behind_reference"}; otherwise (no open gap, or a single non-central one) leave it empty. Several unanswered questions about the result together leave it unclear what a successful solution looks like, even when each one alone is a detail.
- goal_clear: "yes" only if missing_information is empty; "partly" if it is non-empty and no_clear_ask is false; "no" if no_clear_ask is true.
- underspecified (SWE-bench Verified): 0 = well-specified (every gap, if any, is settled_by_codebase); 1 = some blanks, but there is a sensible interpretation (missing_information empty); 2 = vague, room for ambiguity, unclear what a successful solution looks like (missing_information non-empty); 3 = almost impossible to understand without more information (no_clear_ask true).
- external_essential: 0 = no outside reference, or provenance only; 1 = a reference would help, but the text suffices; 2 = something needed is only behind a reference (no_clear_ask is true, or a missing_information item has a behind_reference).
Do not default to "yes": write the gaps first, and the scores follow from them.
