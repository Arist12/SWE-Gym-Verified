You audit one PASS_TO_PASS (P2P) test of a coding task. A P2P test passes on the original code and still passes after the reference fix. A solver's candidate patch passes every FAIL_TO_PASS (F2P) test of the task but fails this P2P test, so the grader rejects it. Decide WHY the candidate fails the test, and which repair, if any, the test needs.

SOLVER-VISIBLE CONTEXT V (apply exactly). The solver (the engineer who resolves the task) sees (1) the task statement: the issue title and body exactly as given in this message, followed by the specification appended to it when the task has one (a "Requirements:" / "New interfaces introduced:" block; the issue text itself is never edited), (2) the full repository at the base commit (neither the fix nor the test patch applied), and (3) the documentation of the pinned dependencies. The solver does NOT see the issue discussion, the pull request, the hidden tests (the test patch), the gold patch (the reference solution), or the content behind links, images and attachments, and it has no network. A passage of the issue discussion reaches the solver only if the specification quotes it.

The task is judged on the task statement as shown to the solver (V), the environment, and the graded tests. The discussion (hints) is NOT visible to the solver; use it only to say that some support exists only there.

REGRESSION-GUARD RULE (one rule for FAIL_TO_PASS checks and PASS_TO_PASS tests)
A regression guard is a check that already passes on the original (base) code: it holds behaviour the base already has. A patch that changes that behaviour fails the guard. The failure counts against the test, not against the patch, only if
(a) the task statement as shown to the solver (V) explicitly asks for the change the check forbids (quote its words), or
(b) the check pins the defect the task statement reports, in a sibling code path or input: the same defect, not merely related behaviour, which a careful fix of the reported defect would naturally also fix (name the sibling path and quote the words that report the defect).
Otherwise the guard protects behaviour that a correct fix must keep, even if the patch's change looks like an improvement, and the failure counts against the patch. Support that exists only in the issue discussion satisfies neither (a) nor (b). A failure that does not depend on the patch (the same test also fails without the patch or with the gold, or the failure comes from the environment: network, randomness, timing, test order, warning-registry state, resource limits, a missing optional dependency) is not a regression-guard failure: it counts neither against the test nor against the patch.

Here the P2P test is the regression guard: it passes on the original code and with the reference fix, and the candidate changes the behaviour it checks. The verdicts below apply this rule.

Verdicts (pick exactly one):
- "pins_old_behaviour": (a) or (b) holds, so the failure counts against the test: the failing assertion requires behaviour that is WRONG by the task statement's own account, either (a) at this test's input, where the statement explicitly asks for the change the assertion forbids (scope "same_input"), or (b) the same reported defect in a sibling code path / input that a careful fix of the reported defect would naturally also fix (scope "sibling"). The reference fix passes only because it fixed the defect more narrowly. The candidate's behaviour on this input is what the statement asks for (it need not be perfect elsewhere). A correct, more complete fix of the stated issue would fail this test.
- "implementation_detail": neither (a) nor (b) holds, and the failing assertion pins an incidental detail that the statement neither asks to change nor needs from a user's point of view (a private or internal name or call, an internal data layout, an incidental message, repr or ordering unrelated to the issue), which the candidate changed as a side effect of fixing the issue. Under the rule the failure counts against the patch, as for "regression"; this verdict only records that the pinned detail is incidental.
- "regression": neither (a) nor (b) holds, and the failing assertion protects behaviour that is correct (not the reported defect, and not the same defect in a sibling path) and that a correct fix must keep; the candidate breaks it. The test works as intended and the candidate is wrong. Changing behaviour outside what the statement covers counts as a regression even if the change looks like an improvement.
- "env_flake": the failure does not depend on the candidate's change (the last sentence of the rule).
- "unclear": the evidence does not decide it.

Do not treat the reference fix as the definition of correct: the question is exactly whether the reference fix is narrower than the statement. Read the test source and the failure output; check the code with repository requests when needed.

Repairs (pick one):
- "state_keep": for pins_old_behaviour with scope "sibling": the task statement can say, in a specification appended to the issue, that the sibling code path or input keeps its current behaviour; the test itself stays as it is;
- "p2p_relax": for pins_old_behaviour when the kept behaviour cannot be stated (scope "same_input": the statement asks for the change): keep the id but narrow the assertion so it accepts both the old and the requested behaviour (say how);
- "keep": the test stays as it is (regression or implementation_detail);
- "flake_drop": the id is an environment flake (env_flake);
- "delete_task": the test cannot be repaired without losing a needed check, or the task is ill-posed.
